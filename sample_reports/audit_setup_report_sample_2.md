# Architecture Decision Points

- **Decision:** Two-copy sync model for SKILL.md (`skills/audit-setup/SKILL.md` + `.claude/skills/audit-setup/SKILL.md`)
  - **Apparent intent:** Contributors opening this repo in Claude Code without `--plugin-dir` flag get the skill automatically via `.claude/skills/`, while `skills/` is the distributable plugin artifact
  - **Cost:** Two files to keep in sync manually; both CLAUDE.md and CONTRIBUTING.md document this requirement, but there is no automated enforcement
  - **Alternative:** Remove `.claude/skills/` and require contributors to use `--plugin-dir .` for local dev; or add a git hook/script to validate sync
  - **Verify with developer:** yes — workflow preference

- **Decision:** No slash commands at plugin root — only under `.claude/commands/`
  - **Apparent intent:** Slash commands are contributor-local only; the plugin distributes skills, not commands
  - **Cost:** Plugin users must rely on skill auto-triggering rather than `/audit-setup`
  - **Alternative:** Investigate whether `commands/` at plugin root is supported (skill-creator has none, suggesting this is correct)
  - **Verify with developer:** yes — confirm whether plugin users are expected to use a slash command or rely on auto-triggering

# Findings

## Finding 1 — CONTRIBUTING.md references non-existent issue templates

- **Severity:** medium
- **Category:** Repo-structure correctness / maintainability
- **Confidence:** high
- **Evidence:** `.github/CONTRIBUTING.md` (lines 7–9) links to three GitHub issue templates: `bug_report.yml`, `feature_request.yml`, and `new_skill.yml`. Neither a `.github/ISSUE_TEMPLATE/` directory nor any `.yml` template files exist in the repo. The links are broken.
- **Why it matters in Claude Code:** Not a Claude Code issue per se, but CONTRIBUTING.md is part of contributor onboarding. Broken links reduce trust and make it harder to file bugs or propose new skills.
- **Expected usage-limit impact:** none
- **Expected runtime impact:** none
- **Context-size impact:** none
- **Repo-structure correctness impact:** medium
- **Quality risk if changed:** none
- **Improvement options:**
  1. Create `.github/ISSUE_TEMPLATE/bug_report.yml`, `feature_request.yml`, `new_skill.yml`
  2. Or: remove the template links and replace with plain GitHub new-issue links until templates are ready
- **Developer assessment needed:** no (option 2 is safe; option 1 is better)
- **Suggested replacement text/config (option 2):**
  ```markdown
  - **Report a bug** — open a [GitHub issue](https://github.com/your-org/claude-code-audit/issues/new)
  - **Suggest an improvement** — open a [GitHub issue](https://github.com/your-org/claude-code-audit/issues/new)
  - **Propose a new skill** — open a [GitHub issue](https://github.com/your-org/claude-code-audit/issues/new)
  ```
- **Files likely affected:** `.github/CONTRIBUTING.md`, `.github/ISSUE_TEMPLATE/` (create if option 1)
- **Proven from runtime evidence or inferred from configuration:** proven — directory does not exist

## Finding 2 — `allowed-tools:` in SKILL.md is not a supported frontmatter field

- **Severity:** low
- **Category:** Claude Code feature completeness / skill metadata
- **Confidence:** medium
- **Evidence:** Both `skills/audit-setup/SKILL.md` and `.claude/skills/audit-setup/SKILL.md` include `allowed-tools: Read, Glob, Grep, Bash, Write` in their frontmatter. The official `skill-creator` SKILL.md uses only `name:` and `description:` — no `allowed-tools:` field. This strongly suggests the field is silently ignored or unsupported.
- **Why it matters in Claude Code:** If the field is ignored, the skill inherits whatever tools the session has — which may be broader than intended. Tool restriction likely needs to happen at the slash command level only.
- **Expected usage-limit impact:** none
- **Expected runtime impact:** none
- **Context-size impact:** none
- **Repo-structure correctness impact:** low
- **Quality risk if changed:** low — removing the field from SKILL.md is safe if the slash command's `allowed-tools:` provides the actual restriction
- **Improvement options:**
  1. Remove `allowed-tools:` from both SKILL.md files; rely on `.claude/commands/audit-setup.md` frontmatter for tool restriction
  2. Keep as-is and verify with Claude Code docs first
- **Developer assessment needed:** yes — verify with documentation before removing
- **Suggested replacement text/config (if removing):**
  ```yaml
  ---
  name: audit-setup
  description: Audit a project's Claude Code setup — context architecture, CLAUDE.md correctness, agents, skills, commands, subagent invocation patterns, tool selection, naming consistency, performance, large-context pressure, usage-limit efficiency, privacy, and maintainability. Produces an audit report with findings and improvement options.
  ---
  ```
- **Files likely affected:** `skills/audit-setup/SKILL.md`, `.claude/skills/audit-setup/SKILL.md`
- **Proven from runtime evidence or inferred from configuration:** inferred — absence in official plugin is strongly suggestive

## Finding 3 — No sync enforcement between `skills/` and `.claude/skills/`

- **Severity:** low
- **Category:** Maintainability
- **Confidence:** high
- **Evidence:** CLAUDE.md and CONTRIBUTING.md both document the requirement to update both SKILL.md copies when a skill changes. There is no automated enforcement: no git pre-commit hook, no CI check, no sync script. Both files are currently identical, but this will drift as the project evolves.
- **Why it matters in Claude Code:** When the two copies diverge, contributors using the repo directly get different audit behaviour than plugin users. This is a silent failure.
- **Expected usage-limit impact:** none
- **Expected runtime impact:** none
- **Context-size impact:** none
- **Repo-structure correctness impact:** medium (future risk)
- **Quality risk if changed:** none
- **Improvement options:**
  1. Add a git pre-commit hook that checks whether the two SKILL.md files are identical; fails the commit if not
  2. Add a `scripts/sync-skills` script that contributors run after editing
  3. Remove `.claude/skills/` entirely and require `--plugin-dir .` (eliminates the sync problem)
  4. Accept manual discipline as the current approach
- **Developer assessment needed:** yes — depends on preferred dev workflow
- **Files likely affected:** `.git/hooks/pre-commit` or `scripts/` (create)
- **Proven from runtime evidence or inferred from configuration:** inferred from repo structure
